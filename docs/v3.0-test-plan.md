# Stampd v3.0.0 — User Acceptance Test Plan

A step-by-step guide for testing the v3.0 release. Designed for QA testers, operations engineers, and adopters evaluating Stampd v3.0.0 against their own deployment.

This document covers the user-visible surface only. For developer-facing implementation details see `internal/implementation/` (gitignored, dev-only).

Each test case has a unique ID (e.g. **T-Scope-01**) so testers can report results unambiguously.

---

## Prerequisites

Before running any test:

- [ ] Stampd.WebApi v3.0.0 deployed in your test environment.
- [ ] Database provider (SQLite for dev, SqlServer / Postgres for stage / prod) reachable.
- [ ] **V16 migration applied** on every database you'll use (see TC-Setup-01).
- [ ] A way to send HTTP requests — `curl`, Postman, or the in-browser Swagger / Scalar UI at `/scalar/v1`.
- [ ] If testing OIDC: access to your external IdP's admin console (Auth0, Okta, Azure AD, Google, Keycloak).
- [ ] If testing SAML2: SAML test IdP credentials (e.g. samltest.id or your enterprise IdP).

### Test environment recommendation

Run against `ASPNETCORE_ENVIRONMENT=Development` for tests T-Scope-* and T-Compliance-*; switch to `Staging` or `Production` for T-Guard-* and T-OIDC-* / T-SAML-* tests where the auth-mode guard's behavior matters.

## TC-Setup-01 — Apply the V16 migration

**Why it matters**: v3.0 introduces the new `AdminScopes` table. Without the migration, `/api/admin/*` endpoints throw on first call.

**Steps**:

1. From the repo root, run:
   ```bash
   dotnet ef database update --project src/Stampd.Infrastructure.Sqlite --startup-project src/Stampd.WebApi
   ```
   (Substitute `SqlServer` or `Postgres` for non-SQLite deployments.)
2. Inspect the database schema. The new table `AdminScopes` should exist with columns `Id`, `UserId`, `TenantId`, `GrantedAtUtc`, `GrantedByUserId`, `RevokedAtUtc`, `RevokedByUserId`, `RevocationReason`, `ConcurrencyToken`.

**Expected**: Migration applies cleanly. No data loss in existing tables.

- [ ] PASS  ☐ FAIL — notes:

## TC-Setup-02 — Bootstrap a super-admin

**Why it matters**: Without at least one admin scope assigned (or a super-admin override), every `/api/admin/*` endpoint returns 403.

**Steps**:

1. In `appsettings.Development.json` (or your equivalent), add:
   ```jsonc
   {
     "Stampd": {
       "Auth": {
         "SuperAdminUserIds": "your-jwt-sub-here"
       }
     }
   }
   ```
   Replace `your-jwt-sub-here` with the `sub` claim that will appear in your dev JWT (e.g. `demo-admin@test`).
2. Restart Stampd.WebApi.
3. Mint a dev JWT via `POST /api/auth/dev-token` with that subject and `roles: ["Admin"]`.
4. Hit `GET /api/admin/dashboard` with the bearer token + `X-Stampd-Tenant: 00000000-0000-0000-0000-000000000001` header.

**Expected**: HTTP 200. Response is the admin dashboard summary JSON.

- [ ] PASS  ☐ FAIL — notes:

## TC-Scope-01 — Grant a tenant-scoped admin

**Why it matters**: Demonstrates the new per-tenant admin model.

**Steps**:

1. As super-admin (from TC-Setup-02), hit:
   ```bash
   curl -X POST http://localhost:5070/api/admin/scopes \
     -H "Authorization: Bearer {your-token}" \
     -H "X-Stampd-Tenant: 00000000-0000-0000-0000-000000000001" \
     -H "Content-Type: application/json" \
     -d '{"userId":"alice@test"}'
   ```
2. Note the returned `id` (GUID).

**Expected**: HTTP 201 Created. Response includes `id`, `userId: "alice@test"`, `tenantId`, `grantedAtUtc`, `grantedByUserId` (your super-admin sub), `isActive: true`.

- [ ] PASS  ☐ FAIL — notes:

## TC-Scope-04 — Revoke and re-grant

**Steps**:

1. Restore super-admin status.
2. Find the scope id for alice (from `GET /api/admin/scopes?activeOnly=true`).
3. Revoke:
   ```bash
   curl -X DELETE http://localhost:5070/api/admin/scopes/{id} \
     -H "Authorization: Bearer {token}" \
     -H "X-Stampd-Tenant: 00000000-0000-0000-0000-000000000001" \
     -H "Content-Type: application/json" \
     -d '{"reason":"end of engagement"}'
   ```
4. Hit `GET /api/admin/scopes` (no filter). Confirm alice's row has `revokedAtUtc` set and `isActive: false`.
5. Re-grant the same userId via `POST /api/admin/scopes`.

**Expected**: Revoke returns 200, scope row's `revokedAtUtc` is non-null. Re-grant creates a NEW row (different id) — audit trail keeps both the revoked and the active row.

- [ ] PASS  ☐ FAIL — notes:

## TC-OIDC-01 — Configure OIDC mode against your IdP

**Why it matters**: Proves v3.0's production-grade SSO path works against your real IdP.

**Steps**:

1. Set in config:
   ```jsonc
   {
     "Stampd": {
       "Auth": {
         "Mode": "Oidc",
         "Oidc": {
           "Authority": "https://your-tenant.auth0.com/",
           "Audience": "https://api.stampd.example.com",
           "RoleClaim": "groups",
           "RoleClaimMappings": {
             "stampd-admins": "Admin",
             "stampd-senders": "Sender"
           },
           "TenantClaim": "tenant_id"
         }
       }
     }
   }
   ```
2. Restart Stampd.WebApi.
3. Sign in via your IdP's hosted login. Capture the access token.
4. Hit `GET /api/admin/dashboard` with the token + tenant header.

**Expected**: HTTP 200 if your IdP-issued token includes `groups: ["stampd-admins"]` AND the user has a matching AdminScope (or is super-admin). HTTP 403 if the role claim is unmapped or no scope.

- [ ] PASS  ☐ FAIL — notes:

## TC-Compliance-01 — HIPAA bundle accepts a B-LT signing request

**Why it matters**: Validates the runtime compliance gate.

**Setup**: Add `services.AddStampdCompliance()` to your composition root (or use the bundled WebApi build that already wires this).

**Steps**:

In your dispatch path or via a small test program:

```csharp
var gate = serviceProvider.GetRequiredService<IComplianceGate>();
gate.Validate(new ComplianceDeclaration(
    Bundle: ComplianceBundle.Hipaa,
    SignatureLevel: "B-LT",
    RequiresIdentityVerification: true,
    SealingProviderIsQesCertified: false));
```

**Expected**: No exception. Request would be accepted by the gate.

- [ ] PASS  ☐ FAIL — notes:

## UI tests (Stampd.UI Blazor app)

> **v3.0 ships no new UI surfaces.** Tenant scope management, OIDC / SAML2 configuration, and compliance bundles are API/config-driven only. The UI tests below are **regression checks** to confirm the v2.3 UI still works correctly against the v3.0 backend (new auth gate, mode selector, V16 migration).

> Run Stampd.UI in `Development` against Stampd.WebApi with `Stampd:Auth:Mode=DevJwt` (default). UI tests for OIDC/SAML production flows require your IdP's hosted login UI, which is outside Stampd's scope.

## What this plan does NOT cover

- **Real SAML2 SSO round-trip** — full assertion validation lands in v3.0.1. The v3.0 SAML2 scaffold returns 501 at the endpoint level; that's by design.
- **Persistent compliance bundle on signing requests** — v3.0 declares the bundle per dispatch via the request body; the typed column lands in v3.1 (V17 migration).
- **Workflow rules engine** — moved to v3.1.

For the full deferred list see `MIGRATION.md` § "What v3.0.0 doesn't ship".
